# Crux2 v1.0.14

The PlayStation 2 emulator PCSX2 as a native homebrew title for a jailbroken PS5 (`PPSA99249`), with a Big Picture interface made for the television and the DualSense.

> [!IMPORTANT]
> **Piracy is not condoned.** This release contains no games, no BIOS files, no console firmware and no decryption keys, and none will ever be provided or linked to. Use only **legally obtained backups of games you own**, made yourself from your own discs, and a BIOS dumped from **a PlayStation 2 you own**. Please don't ask for, or post links to, games, BIOS files, firmware or keys in issues or discussions: they will be removed.

> [!NOTE]
> **An unofficial port.** This is not a build of the PCSX2 project and is not supported by it. Please don't report its problems to PCSX2.

## What's new (since v1.0.0)

Changed in this version: **frames queue while a game is behind.** Crux2 queues no finished frames for the display (*Frames queued for the display: None*, for the least controller delay), so at every frame the emulation waited until the GS thread had finished and shown the frame before. While the GS thread keeps up that costs nothing; in a heavy scene the two took turns instead of working at the same time. In a lit scene of a game I test with, the emulation thread waited about 45% of the time and the GS thread was idle 26%, at 81% speed; with 2 frames allowed to wait, the same scene ran at 95-100% and the session's average went from 86% to 97%. Now, while a game runs below full speed, up to 2 frames may wait, and none again once it has kept full speed for 10 seconds with the GS thread caught up: no added delay while a game keeps up, up to 2 frames while it is behind. *Queue frames while the game is behind* (Graphics > ADVANCED, on) turns it off; a queue of 1-3 frames chosen in *Frames queued for the display* is used as it is. The boot log's `test: window` lines end with `frames queued`.

Changed in v1.0.13: **draws through the rasterizer ordered view keep their render pass.** With accurate blending at light sources, PCSX2 ended and started a render pass for nearly every draw (a game at a light measured about 4,000 a frame for 4,100 draws), because a draw's "reads the picture" and "tests depth" marks changed although, through the ordered view, they had no attachment to act on. They are no longer taken into account for those draws, so consecutive draws stay in one pass; the picture is the same. Statistics shows *passes kept* (`PK` in the `slow:` lines); *Keep the ordered view's render passes* (Graphics > ADVANCED, on) turns it off.

Fixed in v1.0.13: **the graphics switches that take effect at the next start** (*Keep read render targets uncompressed*, *Render targets without compression*, *Leave out barriers with nothing to wait for*, *Reuse copies of the picture*) took effect only when Crux2 started, as the graphics device stays between games; they are read at each game's start now, and the log says which are in effect (`graphics (this game):`). **The boot log's settings line** showed the settings from before a game's database fixes were applied (a game whose fixes set auto flush 2 was logged with 0); it shows them after now, and a `game fixes:` line lists what the game database set.

Also changed in v1.0.13: **built on Mesa 27.0-devel's RADV** (Mesa's main branch, the coming 27.0; Crux2 was on 26.2.5). It does less processor work at each draw, flushes caches less often around queries and barriers, and fixes compressed depth and colour buffers. This is a large driver update and the first build on it: if something draws wrongly, hangs or is slower than before, please send the boot log and say which game and where. Fixed with it: **the graphics chip's own hardware bugs are worked around as for its real generation** (the PS5's chip is a GFX10.1-class part; the driver presented it as GFX10.3 and left the shader compiler's hazard workarounds and two geometry hang guards off). The boot log says `GFX10.1 hardware workarounds on`. Shaders are compiled again once after the update.

Added:
- **Render targets without compression (experimental, off; Graphics > Advanced; at the next start).** Every render target is made without the graphics chip's colour compression, so nothing ever has to be decompressed when a glow, flare or light cone reads it; every other draw moves more data, so it can be faster or slower: compare a scene that slows down with it off and on. The on-screen *decompress* row then reads 0.
- **Barriers skipped and copies reused** on the on-screen Statistics and in the boot log's `slow:` lines (`BS`, `RR`), to see what the two changes below save.
- **Record a GS dump** (the quick menu, under Change disc): 5 seconds of what the game sends the graphics synthesizer, saved to `snaps/` in Crux2's data folder (`/data/crux2/snaps` when that folder exists), with either renderer; the file's name is shown and logged. A dump lets a problem be reproduced on a PC. It holds the game's graphics data: keep it to yourself, don't post it.
- **Slow moments in the boot log.** Whenever a game stays under full speed for two seconds, the log gets a `slow:` line (once a stretch, up to 30 a session): how busy the EE, GS and VU threads and the graphics chip were, and what a frame drew (draws, barriers, render passes, read-backs, copies, decompressions); with paraLLEl-GS, its own status line too. A log from a slow game then says where the time went without reading anything off the screen.
- **Keep read render targets uncompressed (experimental, off; Graphics > Advanced; at the next start).** A render target that a glow or flare reads from itself is kept in the layout that allows it, so the graphics chip no longer decompresses the whole picture each time a draw reads it again. Compare a light source that slows a game with it off and on: the Statistics row *decompress* and the GPU time should drop. If glows or bloom flicker with it on, switch it off and please say so.
- **Statistics on the on-screen display.** With Settings > On-Screen Display > Statistics on, Crux2's panel shows a frame's draws, draw calls, barriers, render passes, copies, uploads and read-backs, and what light-source effects cost in particular: render-pass splits, the graphics chip's full-picture decompressions, destination-alpha passes and copies of the render target. GPU statistics shows the graphics card's time a frame by kind of pass. Standing at a light that slows the game, these say what it pays for.
- **paraLLEl-GS pictures shared with the graphics device (experimental, off).** paraLLEl-GS's picture reaches PCSX2's graphics device through memory both can use, instead of a copy by the processor on the GS thread each frame (about half a millisecond at 1280x896, two at 2560x1792). It takes effect at the next start; if the picture looks wrong with it (stale or torn rows, black), please say so and switch it off.
- **Dithering works with paraLLEl-GS.** Settings > Graphics > Dithering: *Off* and *Force 32 bit* draw without the PS2's dot pattern over gradients; *Force 32 bit* also shows the 32-bit picture a game copies into a 16-bit screen at the end of a frame (the nearest paraLLEl-GS has to PCSX2's 32-bit mode). *Scaled* and *Unscaled* dither as the PS2.
- **paraLLEl-GS counts the game's reads of GS memory** and what they cost. A read of GS memory waits for everything drawn before it (the queue drained, the graphics card caught up), so a game that reads its picture back every frame runs the emulator and the graphics card in turn, with nothing at 100% and the frame rate halved. The on-screen display's processor section gets a *reads* row (the GS thread's time a frame in those waits) while a game reads, and the boot log's `paraLLEl-GS:` status line says how many reads a frame and what they cost.
- **USB controllers (experimental).** Controllers the PS5 does not take itself, plugged into its USB ports: a **DualShock 3 or SIXAXIS** with its pressure-sensitive buttons (d-pad, L1/R1/L2/R2 and the face buttons, as the DualShock 2 had them), its rumble and its player light; **Xbox 360** pads; **guitars, drums** and other USB pads. Switch on Settings > Controllers > *USB controllers (experimental)*, then a port's *Map it to a USB controller*; for the rhythm games set the port's controller type to *Guitar*. This had not been tried on a console when this release was built: the boot log says how it went in lines beginning `usb pads:`, and when the console refuses, only its own controllers are used, as before. Logs either way are very welcome.
- **Console language.** Settings > BIOS > *Console language*, or in a game's own options: the language games are told the PlayStation 2 is set to, for the many European games that pick theirs from it. *As the BIOS has it* keeps the BIOS's own, and the BIOS's setting is never changed. It takes effect at the game's next start, and the boot log says `bios: the game is told language …` when it is used.
- **paraLLEl-GS's figures.** The on-screen display's GPU section shows paraLLEl-GS's own graphics card time a frame (from its timestamps; PCSX2's GPU figure sees only PCSX2's device, which does little while paraLLEl-GS draws), its shading part and the samples a pixel; the processor section its thread (*PGS*) and how long the GS thread waited for it (*wait*). The boot log has the same line every 30 seconds while a game runs. When paraLLEl-GS is slow, these say whether the graphics card is the limit.
- **Automatic quality with paraLLEl-GS.** When the graphics card cannot keep the game at full speed, the samples a pixel go down a step (16, 8, 4, 2, 1) for as long as it needs to, and back up when there is room again, said on the screen as the resolution steps are. What you chose stays what you chose.
- **The PlayStation 2 menu.** Settings > BIOS > *Start the PlayStation 2 menu*, or the library's Square menu: the PS2's own browser and its System Configuration (clock, language, screen).

Changed:
- **Fewer waits at light sources.** A draw that reads the picture it draws on (glows, flares, light cones, PCSX2's accurate blending) made the graphics chip finish everything before it each time. It now waits only when something was drawn there since the last wait; when nothing was, the last wait already covers it, so the picture is the same. *Leave out barriers with nothing to wait for* (Graphics > Advanced, on) turns it off.
- **Fewer copies at light sources.** A copy of the picture that a glow or blur reads (with native scaling, or where it reads another part of the picture) is used again while nothing has been drawn into the picture or the copy since. *Reuse copies of the picture* (on) turns it off; please do if an effect ever looks a frame behind, and say so.
- **paraLLEl-GS compiles its shaders ahead.** It compiles the shaders a game needs in the background, those the game used the last time first, and keeps the compiled ones between sessions (`pgs-pipeline-cache.bin` in the title folder, checked against the driver and the shaders before use): far fewer pauses when a game starts or a new scene comes. The first start after an update compiles again.
- **Glow and flare draws keep their render pass** (PS5 only): PCSX2 v2.9.142 ends and starts the render pass around every draw that samples the screen it draws to; on this graphics chip a barrier inside the pass does the same, so the pass is kept, as before.
- **Automatic quality keeps paraLLEl-GS at 4 samples or more** while its picture is at twice the size: below 4 the picture fell to the PS2's own size.
- **NIS enlarges up to 2x and FSR 1 takes over past that** (a paraLLEl-GS picture to a 4K screen is about 2.4x), instead of the screen's plain filter.
- **The paraLLEl-GS samples setting says what each costs**: with the picture at twice the size 4 and 8 give the same size (8 smooths a little more for about twice the work); 16 with it is the sharpest.
- **Built on PCSX2 v2.9.142** (was v2.9.138): Vulkan barriers where a draw samples its own render target, and accuracy fixes in the hardware renderer (render-target alpha with SCANMSK, transfers kept longer in the texture cache's history).
- **Built on Mesa 26.2.5's RADV** (was 26.2.0): the stable releases' fixes for this graphics chip's generation, among them binning, sRGB clears, depth/stencil resolves, sampler lifetimes and shader compiler fixes.
- **paraLLEl-GS's samples and its picture at twice the size change while a game runs** (they waited for the next start).
- **paraLLEl-GS hands the graphics card its work as it goes, as a setting** (*paraLLEl-GS hands work over as it goes (experimental)*, off): v1.0.8 had it always on and it broke pictures (below); it is fixed, and off until it is proven on the console. With it on: it used to hand over a frame's work only at the frame's end, at a read of GS memory, or after a few thousand primitives, so a game that reads its picture back waited for the graphics card to draw the whole frame from the start. Now its thread hands over what it has recorded whenever it has nothing else to do (and at least every millisecond while busy), so at a read most of the frame is drawn already. What the game reads is unchanged. Its thread also keeps taking the game's next frame while a finished picture comes back, instead of stopping for it. The boot log's `paraLLEl-GS:` line now says how much of the reads' cost was the graphics card and how often work was handed over early.
- **Hardware download mode works with paraLLEl-GS** (Settings > Graphics > Advanced): *Unsynchronised* answers a read of what the graphics card has not finished with zeros instead of waiting for it, *Off* reads nothing; both faster, both wrong where the game uses what it read (a missing effect, a black picture). *Accurate* and the other modes wait and are right, as before. If the on-screen *reads* row is most of a frame, this setting is where the speed is.
- **Renderer is one choice**: Hardware (Vulkan), Software, paraLLEl-GS; paraLLEl-GS's own rows follow it.
- **paraLLEl-GS takes the display settings.** Deinterlacing (*Automatic*: a progressive picture where the game allows it; any other choice: the fields as the PS2's own scan-out blended them), Anti-blur, Screen offsets, Show overscan and Mipmapping now reach paraLLEl-GS, and change while a game runs. The settings it has no equivalent of (the internal resolution, texture filtering, dithering, blending accuracy, the hardware and upscaling fixes, texture packs, Disable interlace offset) are greyed out while it is on, and the paraLLEl-GS row says which is which. Before, it drew with fixed scan-out settings whatever Settings said.
- **The on-screen display is one panel**, in sections as PC overlays show them: the graphics chip (its load and time a frame), the processor (the emulator's threads; with Hardware info its temperature and clock where the console tells them, and the memory in use) and the frames (FPS, frame time, max, average, min, 1% and 0.1% lows) with a graph of the frame times. Settings > On-Screen Display > Style has PCSX2's own lines back.

Fixed:
- **The GS dump hotkeys** recorded nothing while paraLLEl-GS drew (they record through it now), and their messages were not shown; a press shorter than a frame no longer records nothing.
- **The graphics driver's shader cache could switch itself off** on the console since v1.0.8 (Mesa 26.2.5 maps its index in a way the console may refuse; it falls back now).
- **paraLLEl-GS dithered 32-bit frame buffers**, which the PS2 does not do: a fine pattern, and glows and blurs drawn over several passes came out darker. It dithers 16-bit frame buffers only now. Two related corrections: a blend that leaves a 16-bit colour as it was is no longer skipped when dithering still changes it, and a palette offset past the palette's end (a game's mistake) no longer writes outside it.
- **paraLLEl-GS blended alpha masks at polygon edges** at 4 and 8 samples: a mask of 0 or 128 came out 64 along edges, and passes that read it (shadows, glows, destination alpha) showed fringes. Colours are still averaged (smooth edges); alpha is the value most of the pixel's samples hold.
- **paraLLEl-GS drew a picture of dots, or froze with the sound going on** (v1.0.8, every download mode): handing work over early could upload a texture before the pass that decides what of it to upload, and recycled memory the frame was still using.
- **The D-pad's Up and Down stopped working** after stepping Renderer through Software with Left/Right: the graphics device starts again on such a change, and a D-pad release in that moment was lost, so Up/Down were then taken for diagonals and ignored.
- **Hardware download mode *Off* still made paraLLEl-GS wait for the graphics card** at each read the game made, though nothing used what it read.
- **Opening Settings stopped Crux2** (v1.0.1 and v1.0.2): the controllers page read a setting while it already held the settings' lock.
- **Switching on an on-screen figure showed nothing:** the first release left the figures' place at "Not shown". It is the top right again, and switching a figure on while it is "Not shown" moves it there.
- **Games played one after another slowed down and hitched:** the game before's render targets and textures (hundreds of MB at 6x) stayed in the graphics device's pool. They are let go when a game closes, and the boot log says how much memory there is at each game's start and end.
- **The PS2's start-up ran at double speed at 120 Hz** with frames paced by the screen, until Crux2 caught it a few seconds later. The game can no longer run ahead of its own rate while the screen paces, from the first frame.

## Tested for this release

On the PC: the host and feature tests, the settings' lock check, the interface tests (every settings row changed every way, 315,457 and 309,669 frames of random button presses with the sanitizers, 20,082 pictures of the screens, 0 failed) and the release check pass.

On the console, with the v1.0.13 build: Mesa 27.0-devel's RADV with the GFX10.1 workarounds on, in the heaviest scenes I test with, without a hang or a wrong picture; the render passes at light sources went from about 4,000 a frame to about 40. The change in this version was measured on the console by setting *Frames queued for the display* to 2 frames by hand (81% to 95-100% in the same scene, above); the automatic switch itself, built for this version, has not run on the console yet.

## Known issues

- USB controllers are untested on a console (above).
- paraLLEl-GS is slower than PCSX2's renderer in the heaviest game I test with, and its picture is softer by design. A game that reads its picture back every frame runs at half speed under it with Hardware download mode *Accurate* (the *reads* row says so).
- The free BIOS is early work: many games reach their menus and go no further. Use a BIOS dumped from your own PlayStation 2.
- RetroAchievements' hardcore mode is not offered.

## Install or update

1. Copy the `PPSA99249` folder from the ZIP to your homebrew folder on the console (`/data/homebrew/`), over an older one if you have it.
2. Your settings, memory cards, states and games stay: with a folder `/data/crux2`, Crux2 keeps them there, outside the title folder.
3. Your own games in `games/` (or on a USB drive or a share), your own BIOS in `bios/`. None included, none ever will be.
4. Read `LEGAL.txt` and `README.md` in the folder.

## Reporting problems

Open an issue with `crux2-boot.log` and `logs/emulog.txt` from the title folder (Settings > System can copy them to a USB drive), copied before Crux2 is started again. Never attach games, BIOS files, firmware or keys.
